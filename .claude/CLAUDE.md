# プロジェクト運用ルール

このプロジェクトでの開発方針を定める。下記は **MECE（重複なく・漏れなく）** で整理した
8つの領域からなる。各ルールはいずれか1領域にのみ属する。Claude（および作業者）は
本方針に従うこと。これらは既定の挙動より優先される。

---

## 1. 着手前 — 方向性と仕様の確定

実装に入る前に、まず方向と仕様を固める。コードを書き始めるのは最後。

- **ロードマップ（方向性）を先に再確認する。** 何を作るのか、今やるべきことは何かを
  共有・合意してから動く。いきなり実装に飛び込まない。
- **曖昧な仕様を残したまま実装しない。** 仕様書・要件に曖昧点や矛盾があれば、実装前に
  すべて洗い出し、ユーザーの判断を仰いで確定させる。
- 「この時点で、ほかに詰めるべき仕様はないか？」を着手前に必ず自問・確認する。
- 確定した決定事項は、後続が迷わないよう仕様ドキュメント等に書き残してから実装に進む。

## 2. ローカル作業 — ブランチとコミットの進め方

ローカルかつ可逆な作業は、ユーザーの逐次指示を待たずに進めてよい領域。

- **作業ブランチを切ってそこで作業する。** `main` 上で直接作業しない。
- **既存の作業ブランチがあれば再利用する。** 用もなく新しいブランチを増やさない
  （散らかり防止。環境によってはリモートブランチを消せないため。→ 領域6・領域8参照）。
- コミットは小さく、メッセージは何をなぜ変えたかが分かるように書く。
- 作業ブランチへの **commit・push までは進めてよい**（push 自体は外向きだが、作業ブランチの
  更新は可逆で安全なため許可。ただし `main` への push は領域3で禁止）。

## 3. 統合ゲート — PR・マージ・main 反映（ユーザー承認が必須）

「main に何が入るか」を決める操作は、すべてユーザーがゲートを握る。Claude は独断で行わない。

- **`main` へ直接コミット／push しない。** ユーザーの明示的な許可がない限り禁止
  （Git を使う意味がなくなるため）。
- **PR の作成は、ユーザーが明示的に指示するまで行わない。** 勝手に PR を立てない。
- **PR のマージは、ユーザーが明示的に指示するまで行わない。** 勝手にマージしない。
  自動マージ（auto-merge）の有効化も同様に指示待ち。
- 「作業ブランチへの push までは Claude、PR を立てる／マージするのはユーザー」を境界とする。
- 補助として PreToolUse フック（`.claude/hooks/dev-policy-gate.py` ＋ `.claude/settings.json`）で
  **PR の作成・auto-merge をユーザー確認（ask）** に倒している。ただし
  **`main` 直 push と PR マージの機械判定はフックに入れていない**（→ 領域8の経緯メモ。
  マージは実務上「ユーザーの明示指示 → 実行」の流れであり、指示済みでも毎回確認が出るのは
  冗長なため 2026-07-13 に除外）。それらは本ルール（人間可読）で守る。
  フックは保険、まず本ルールに従うこと。

## 4. その他の外向き・不可逆操作 — 独断禁止

領域3（PR・マージ）以外で、外部に影響する／戻しにくい操作も独断で行わない。

- 履歴の書き換え（force push、`rebase` 後の強制更新、`reset --hard` での共有履歴改変）は
  事前確認する。
- 外部サービスへの送信・公開（パッケージ公開、デプロイ、外部 API への投稿・コメント等）は
  事前確認する。一度出したものはキャッシュ／インデックスされ得る。
- 既存ファイル・データの削除や上書きは、対象を確認し、説明と矛盾する内容や自分が作って
  いないものなら、進めずに報告する。
- 迷ったら「やってよいか」を先に確認する。承認は文脈ごと。一度の許可を別の操作へ広げない。

## 5. ブランチのライフサイクル — 整理と統合

ブランチを散らかさず、完成したら main に集約する。

- 機能・修正は基本的にすべて `main` にマージして統合する。別ブランチに置いたまま放置しない
  （どの機能が main にあるかを誤解させないため）。
- **統合（マージ）が完了したら、不要になったブランチは削除する。**
  - ローカルブランチは通常どおり削除してよい。
  - リモートブランチは、削除できる環境なら統合済みであることを確かめたうえで削除する。
    できない環境ではユーザーに依頼する（領域6参照）。
  - 例外: `main` は削除しない。作業中で未統合のブランチは残してよい。

## 6. 実行環境の制約 — 環境によって変わる

**2026-08-31 改訂。この節はかつて「リモートブランチを削除できない」と断定していたが、
それは当時のクラウド実行環境に固有の制約であり、環境が変われば当てはまらない。**

| 環境 | リモートブランチの削除 |
|---|---|
| クラウド実行環境（〜2026-08-30） | **不可。**`git push --delete` を git プロキシが HTTP 403 で拒否し、GitHub MCP にも `delete_branch` 系のツールが無かった。認証や `gh` の不在が原因ではなく、作成・更新・push は正常にできていた |
| Windows 実機 ＋ `gh` CLI（2026-08-31〜） | **可。**`git push origin --delete <branch>` が通ることを実測で確認した |

したがって次のように扱う。

- **まず自分の環境で削除できるかを確かめる。**できるなら、統合済みのブランチは自分で削除する。
  削除の前に、`git merge-base --is-ancestor` と `git log <main>..<branch>` で**未統合の
  コミットが無いこと**、およびそのブランチを参照する未処理の PR が無いことを必ず確認する。
- 削除できない環境では、**使い捨てのリモートブランチを作らない**（消せずに残るため。
  既存ブランチを再利用する。→ 領域2）。削除が必要なときはユーザーに依頼する
  （`https://github.com/<owner>/<repo>/branches`）。
- **デフォルトブランチは削除できない**（GitHub の仕様）。「Automatically delete head branches」を
  有効にしていても、マージ時点でデフォルトブランチだったブランチは自動削除の対象外になる。

## 7. コミュニケーションと報告

進め方と結果の伝え方。

- **結果は正直に報告する。** テストが失敗したら出力とともにそう言う。スキップした手順は
  スキップしたと言う。完了・検証済みなら、はっきりそう言い切る。
- **ミスは言い訳せず認める。** 取り繕わない。
- 食い違い・予期せぬ結果・判断の分岐は、**なぜそうなったかを筋道立てて説明**する。
- 判断がユーザーに属するとき（方向・仕様・外向き操作）は、勝手に決めず確認する。
- **確認は通常のメッセージ（テキスト）で行う。AskUserQuestion（選択肢UI）は、ユーザーが
  明示的にその形式を指示したとき以外は使わない**（クラウド形式の開発では選択肢UIが
  すぐタイムアウトするため。ユーザー指示 2026-07-14）。

## 8. 方針の維持と伝播

決めたことを毎回ブレさせず、別の開発にも伝える。

- 合意した運用方針は本ファイル（`.claude/CLAUDE.md`）に記録し、リポジトリと共に伝播させる。
- 同じ方針をユーザー全体メモリ（`~/.claude/CLAUDE.md`）にも置き、ローカルの全プロジェクトへ
  効かせる（ただし Web/リモート環境ではコンテナ再生成で消えるため、リポジトリ内が確実）。
- 機械的補助として、`.claude/settings.json` の PreToolUse フックで **PR の作成・
  auto-merge をユーザー確認（ask）** に倒す（領域3の保険）。
- 新しいリポジトリへは、本方針を運ぶスキル **`dev-policy`** を使って、`.claude/CLAUDE.md` を
  ひな形として展開する。

### 経緯メモ: フックの守備範囲

- 当初は「main 直 push＝deny／PR 作成・マージ＝ask」を1つのフックで強制していたが、
  main 直 push の機械判定（Bash コマンド文字列の正規表現マッチ）は無害なコマンドまで誤爆し、
  回避も容易で設計が難しいため、**その判定だけ外した**。main 直 push 禁止は
  人間可読ルール（領域3）で守る。
- **2026-07-13: マージの確認（ask）も外した。** マージは実務上ユーザーの明示指示を
  受けてから実行する操作で、指示済みでも毎回フックの確認が出るのは冗長だったため
  （ユーザー判断）。今フックが見るのは **PR の作成と auto-merge 有効化**
  （GitHub MCP ツール名）だけ。独断マージの禁止自体は人間可読ルール（領域3）で守る。
- 過去の実装はコミット履歴から辿れる（履歴の書き換えはしていない）。

## 付則: SigK PDF 固有の方針

上記8領域は CheckListMaker から `dev-policy` スキルで展開した共通方針である。本リポジトリ
固有の事情を以下に足す。共通方針と矛盾する場合は共通方針を優先する。

### A. 技術構成は CheckListMaker に揃える

本アプリは CheckListMaker と同じ作者・同じ配布形態（Windows・NSIS インストーラー）である。
学習コストと保守の分散を避けるため、次を踏襲する。詳細は `docs/02_アーキテクチャ設計.md`。

- Electron ＋ CommonJS ＋ 素の HTML/CSS/JavaScript。**ビルドステップを置かない**
  （TypeScript・React・バンドラーを導入しない）。
- `preload.js` は `contextBridge.exposeInMainWorld` で機能ごとに名前付き API を公開し、
  各 API に `available: true` を持たせる。
- IPC のチャンネル名は `領域:動作`（例 `pdf:open`・`merge:run`）。
- テストは `node --test` ＋ jsdom。画面テストは `test/harness.js` が返す `window.SigK` 経由で
  内部 API に触る（テスト専用のフックは別に持たない）。
- 外部 CDN・Web フォント・アイコンライブラリを参照しない。アイコンはインライン SVG を自作する。

### B. 単一 HTML への集約はしない

CheckListMaker の `index.html` は 388KB の単一ファイルに CSS・JS を同居させている。本アプリは
機能数が多く、そのままでは早期に破綻する。**ビルドステップを置かない方針は維持したまま**、
レンダラーを役割ごとの `.js` に分割し `index.html` から `<script>` で読み込む
（`docs/02_アーキテクチャ設計.md` 第4章）。

### C. PDF を壊さないための不可逆操作の扱い

領域4（外向き・不可逆操作の独断禁止）を、本アプリのドメインへ具体化する。

- **上書き保存はユーザーの明示操作でのみ行う。** 自動保存を実装しない。
- **フラット化・墨消し・ページ削除の確定など、元に戻せない加工は実行前に確認を出す。**
- 出力先に同名ファイルがある場合は、黙って上書きしない。
- 開発中のテストで、ユーザーの実ファイルを入力に使わない。`test/fixtures/` の検証用 PDF を使う。

### D. 商標・トレードドレスに関する禁止事項

`docs/00_調査要件レポート.md` 第7章の結論を、実装時の禁止事項として運用する。点検項目は
`docs/06_ライセンス・商標チェックリスト.md` に一覧化してあり、リリース前に必ず通す。

- 製品名・画面表示・コミットメッセージ・ドキュメント・訴求文言に「Adobe」「Acrobat」
  「PostScript」および他社製品名を書かない。互換性を示す表現も使わない。
- 既存商用 PDF 製品の配色・アイコン・ツールバー配置を模倣しない。
- 依存 OSS を追加したら、その場で `THIRD-PARTY-NOTICES.md` に追記する。ライセンスが
  AGPL・GPL のものは、同梱する前に必ずユーザーへ確認する。
