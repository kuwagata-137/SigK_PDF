## 目的

塊③-b までで **読む**側は揃った。開いて、並べて、探して、紙に出せる。
ここから先は **直す**側である。塊④ はその第一歩で、**ページの並びを組み替える**ところまでを担う。

- **ページモードが空である。**ツールレールの「ページ」を押すとタイトルが変わり、
  サイドパネル下部に操作ボタンが4つ出るが、**4つとも `aria-disabled` のまま**で、
  しかもサムネイル自体が消える（閲覧モード専用にしてあるため）。何もできない。
- **`ops` を組み立てる場所が無い。**`docs/02` 2-3 は編集内容の持ち方を定めているが、
  実装は1行も無く、後述のとおり**設計に穴がある**。
- **Ctrl+Z / Ctrl+Y / Delete は `docs/04` 第8章で予約済みだが動かない。**

塊④ で「並べ替え・回転・削除・複数選択・元に戻す」を入れ、**編集した結果を画面に映す**。
ファイルへ書き戻すのは塊⑤ である。

## 事前調査

仕様を決める前に、**実物のコードと実物の pdf-lib で確かめた**こと。推測で書いた設計を
実装で覆さないためである（塊③-b で同じ手順が効いた）。

### 既存コードの実測

| 調べたこと | 分かったこと |
|---|---|
| ページモードは今なにをしているか | `shell.js` の `setMode()` が `data-mode` 属性・レールの `active`・`#side-title`・`#side-actions.hidden` の4つを変えるだけ。さらに `thumbnails.refresh()` を呼ぶが、閲覧モード以外では `discard()` されるため**サムネイルは消える** |
| サイドパネルの操作ボタン | `#side-actions` に **`div.act` が4つ**（左回転・右回転・抽出・削除）。`id` が無く、`button` でもなく、`tabindex` も `role` も無い。**有効にしてもキーボードから押せない**。`.side-actions` は `grid-template-columns:1fr 1fr` の2列固定 |
| サムネイルの多列化 | `layoutThumbnails()` は**1列専用**。列数の引数が無く、返す `page` に `left` が無い。`.thumb{left:0}`（`shell.css:133`）も1列前提。直す箇所は `viewer-layout.js`・`thumbnails.js`・`shell.css` の3つ |
| ページ選択という概念 | **どこにも無い。**「現在のページ」（`current`、単数）しか無い |
| ドラッグ並べ替えの下地 | 無い。`file-drop.js` は**ファイルのドロップ専用**で、`types.includes('Files')` で判定しているため、**ページ内どうしのドラッグではオーバーレイは出ない**（干渉しない）。ポインタ操作の作法は `shell.js` のサイドパネル用つまみに前例がある |
| ページ数の出どころ | `viewer.getState().pageCount` は `doc.numPages` ではなく **`state.sizes.length`**。`state.sizes` を編集後の並びで作り直せば、ページ番号入力・Home/End・印刷範囲・検索の走査本数は**自動で追従する** |
| `doc.getPage()` を直に呼ぶ場所 | **`page-render.js:83` と `thumbnails.js:158` の2か所だけ**。`find.js` と `print.js` は `viewer.getPage(number)` の1本を通っている。つまり写像を入れる場所は実質3か所 |
| ステータスバーのページ数 | `open()` の中で `doc.numPages` から**1回だけ**書き、以後どこも更新しない。編集しても取り残される（要修正） |
| サムネイルの持ち物 | `thumbnails.js` は `setDocument({doc, sizes, ...})` で **doc と sizes の写しを自前に持つ**。公開 API 7本に「並びだけ差し替える」口が無く、`setDocument` を呼び直すとスクロール位置と描画済みを全部捨てる（口を1本足す） |
| 検索の状態 | `find.js` の `state.pages` と `matches[].page` は**ページ index**。編集で一斉にずれるが、無効化する入口が `clear()`（文書を閉じるときだけ）しか無い |
| 開いたバイト列 | pdf.js の `getDocument` は `data` の `ArrayBuffer` を **transferable としてワーカーへ渡す**。`viewer.open()` の時点でレンダラー側の `Uint8Array` は detach され、**どこにも残らない**。保存はパスから読み直すことになる（塊⑤） |
| キーの空き | メニューは「ファイル」「ヘルプ」だけで **`editMenu` ロールを持たない**ので、Ctrl+Z / Ctrl+Y / Ctrl+A はレンダラーの `keydown` に届く。ただし `viewer-controls.js` の `handleKey` は `event.ctrlKey` で早期 return するため、いまは素通りしている |
| アイコン | 20個。`rotateLeft`・`rotateRight`・`extract`・`trash` はある。**`insert`・`undo`・`redo` が無い** |
| pdf-lib の読み込み | `index.html` の `<script>` 19本に **`vendor/pdf-lib.min.js` は入っていない**（525KB）。塊④ はレンダラーで pdf-lib を使わないので、読み込まないままにできる |

### 回転を画面へ映せるか（pdf.js 側）

| 調べたこと | 分かったこと |
|---|---|
| `getViewport` は回転を受けるか | **受ける。**既定値はページ自身の `rotate`。渡した値は**絶対値として置き換える**。`PageViewport` が 360 で剰余し、負値に +360 するので `page.rotate + 90` や `- 90` をそのまま渡してよい。**90 の倍数でない値だけ例外**になる（pdf.js は `rotate` を 90 の倍数に正規化して持つので、実際には起きない） |
| `getViewport({scale})` を回転なしで呼んでいる場所 | **4か所。**`page-render.js` の描画、`page-render.js` のテキストレイヤー、`thumbnails.js` のサムネイル、**`print.js` の 150dpi 画像**。4つ目を忘れると「画面では回っているのに印刷は回っていない」が起きる |

### pdf-lib 側（塊⑤で効くが、いま決めておくべきもの）

実物の pdf-lib 1.17.1 を動かして確かめた。**塊④ ではファイルへ書かないが、
書けない設計を塊④ で作らないため**に先に調べた。

| 調べたこと | 分かったこと |
|---|---|
| 同一文書内の並べ替え | `removePage` ＋ `insertPage` で、注釈・リンク・しおりが保たれる。`/Names` の宛先も保たれる |
| `PageLabels` | **追従しない。**並べ替えても catalog の `/PageLabels` はそのまま残るため、ラベル付き文書では保存後にラベルがずれる。本アプリの画面は 1..N の連番なので**画面上は分からず、他のビューアで開いたときだけ見える** |
| 削除でファイルは小さくなるか | **ならない。**1,000ページ・195.7MB から 500ページ削除して保存しても、出力は 195.7MB のまま |
| `copyPages` での複製 | しおり（outlines）と AcroForm が**必ず消える**。挿入では、運ばれた内部リンクの飛び先がページ木の外を指し、**壊れたリンクと余分なページオブジェクトが混入する** |
| `setRotation` | **絶対値**で、正規化しない。0/90/180/270 以外や負値をそのまま入れられる。pdf.js の扱いと食い違うので、**正規化は1か所で1回だけ**行う決めが要る |
| 全ページ削除 | `save()` の既定 `addDefaultPage:true` により、**黙って白紙 A4 が1枚生える** |
| メタデータ | 既定 `updateMetadata:true` で Producer が pdf-lib に書き換わる |
| 【重大】和文フォーム PDF | `save()` の既定 `updateFieldAppearances:true` が、`/AP` を持たない欄の見た目を **Helvetica（WinAnsi）で作り直す**。日本語の値が入った欄があると、**ページを1枚消しただけで `WinAnsi cannot encode "氏"` で保存が失敗する**。`save({updateFieldAppearances:false})` なら成功し、値も保たれる |
| 進捗・中止 | `save()` の引数は4つだけで、**進捗のコールバックも中止の手段も無い**。`docs/04` 第6章の「1秒を超えそうな処理は進捗と中止」に対し、進捗は save の中ではなく**外側（読み込み／適用／書き出しの3段）でしか出せない** |
| 想定上限での実測 | 1,000ページ・195.7MB で load 526ms・全ページ逆順の並べ替え 16ms・save 1,634ms。rss は読み込み直後 251MB、save 直後 470MB、続けて2本目を扱うと 678MB |
| pdf.js で開けて pdf-lib で開けない文書 | **ある。**内容が欠損した PDF では `load` が例外になり、しかも素の `TypeError`（`Cannot read properties of undefined (reading 'Pages')`）が混じる。警告は `console.warn` へ直接出るため `log:error` に載らない |

**この節の結論**: **並べ替え・回転・削除そのものは 16ms で終わる。**重いのは読み込みと書き出しで、
どちらも塊⑤ の担当である。塊④ を「画面の上の計画づくり」に閉じれば、
pdf-lib をレンダラーへ持ち込まずに済む。

## 確定事項

### A. 編集内容の持ち方（`docs/02` 2-3 の改訂）

`docs/02` 2-3 は編集を **`ops`（操作の列）** で持つと定めている。実物に当てて調べたところ、
**4つの穴**があった。

1. `reorder` / `rotate` / `delete` のページ番号が**いつ時点のものか**が定義されていない。
   `delete` の後の `rotate` は削除前の番号か、削除後の番号か。
2. `rotate` の `degrees` が**絶対値か相対値か**が定義されていない。
   pdf.js（絶対）と pdf-lib（絶対）に対し、UI は「右へ90度」という相対の操作である。
3. **抽出・挿入の op が無い。**
4. **undo が書けない。**`docs/02` は「undo/redo が操作の列の巻き戻しとして自然に書ける」と
   するが、各 op に逆操作が無く、ページの同一性（どの op のどのページが同じページか）も
   無いため、列を1つ削っても元の状態には戻らない。

| # | 論点 | 決定 |
|---|------|------|
| 1 | 編集の表し方 | **「操作の列」ではなく「結果の並び」で持つ。**編集の状態は `plan` という配列1本で、要素は `{ src, rotate }`。`src` は**元ファイルの 0 始まりページ番号**、`rotate` は**元ページの `/Rotate` に足す相対角度**（0/90/180/270）。表示・印刷・保存はすべてこの配列だけを見る |
| 2 | なぜ結果の並びか | ① 時点の曖昧さが消える（配列は常に「いま」を表す）② undo がスナップショット列で書ける ③ 適用が冪等（同じ plan を何度当てても同じ）④ 並べ替え・回転・削除はすべて配列の操作に落ちる |
| 3 | `docs/02` 2-3 の扱い | **`ops` を捨てるのではなく、住み分ける。**ページの並び（並べ替え・回転・削除・抽出・挿入）は `pages`（＝ plan）で、ページに**足す**もの（注釈・透かし）は従来どおり `ops` で送る。ワーカーへ渡す形は `{ source, pages, ops, target }`。→ **論点4** |
| 4 | 回転の正規化 | **`page-plan.js` の1か所だけで行う。**`rotate` は常に 0/90/180/270 に丸めて持つ。画面へ渡すときは `page.rotate + plan[i].rotate`（pdf.js が 360 で剰余する）。保存時は `((元 + 相対) % 360 + 360) % 360` を `setRotation` へ渡す |
| 5 | plan の初期値 | 文書を開いた時点で `[{src:0,rotate:0}, {src:1,rotate:0}, ...]`。**編集していない状態も plan で表す**（特別扱いを作らない） |
| 6 | dirty の判定 | plan が初期値と一致しなければ dirty。**配列の比較で決める**（操作した回数では決めない。3回回して元に戻したら dirty ではない） |
| 7 | plan の置き場所 | **タブごと**（`spec-1-2` 確定事項2 の session）。タブを切り替えても編集内容が残る |

### B. 元に戻す・やり直し（F-02-7）

| # | 論点 | 決定 |
|---|------|------|
| 8 | 持ち方 | **plan のスナップショット列。**`{ stack: [plan0, plan1, ...], at: n }` を持ち、Ctrl+Z で `at` を1つ戻し、Ctrl+Y で1つ進める。逆操作を書かないので、操作の種類が増えても undo の実装は増えない |
| 9 | 履歴の上限 | **50世代。**超えたら古いほうから捨てる。plan 1本は1,000ページでも要素1,000個（数十KB）なので、50世代持っても数MBに収まる |
| 10 | 履歴の分岐 | 戻した状態から新しい操作をしたら、**先の履歴は捨てる**（一般的な作法） |
| 11 | 履歴の範囲 | **タブごと。**別のタブの操作は混ざらない。文書を閉じたら履歴も捨てる |
| 12 | 選択は履歴に入れるか | **入れない。**選択の変更では undo できない。ただし戻した直後の選択は、**その世代で操作の対象だったページ**に合わせる（何が戻ったか分かるようにする） |
| 13 | 履歴に積む単位 | 1回のユーザー操作で1世代。ドラッグ1回の並べ替え、回転ボタン1回、削除1回がそれぞれ1世代 |

### D. サイドパネルの多列グリッド

| # | 論点 | 決定 |
|---|------|------|
| 23 | 列数 | **パネルの幅から自動で決める。**`列数 = 1〜3 の範囲で floor((内容幅 + 10) / 110)`。目標の紙幅は 100px。実測値は 幅180px→1列（紙150px）／240px→2列（95px）／300px→2列（125px）／340px→3列（90px）／420px→3列（117px）。固定の2列にすると最小幅で紙が 65px まで縮む |
| 24 | なぜ自動か | サイドパネルは 180〜420px でドラッグできる（`shell.js`）。固定列にすると、どこかの幅で必ず破綻する |
| 25 | `layoutThumbnails` の改修 | 引数に `columns` を足し、返す `page` に `left` を足す。**1列のときの返り値は今と同じ**にする（閲覧モードの回帰を防ぐ） |
| 26 | 同時に持つサムネイルの上限 | **`24 × 列数`**（1列24・2列48・3列72）。多列では紙が小さくなるため、枚数が増えても総メモリは1列時を下回る（幅240pxで 1列210px 対 2列105px ＝ 面積比4倍） |
| 27 | 列数が変わったとき | 枠を作り直し、描画済みを捨てる。パネルの幅変更で既に同じ経路が動いている（`spec-1-3` 確定事項15） |
| 28 | 閲覧モードのサイドパネル | **変えない。**1列のまま。ページモードだけ多列にする |
| 29 | モードを切り替えたとき | サムネイルを捨てずに**並べ直す**。`thumbnails` に `setPlan(plan)` と `setColumns(n)` を足し、`setDocument` の呼び直し（スクロール位置と描画済みを全部捨てる）を避ける |

### E. 並べ替え（F-02-1）

| # | 論点 | 決定 |
|---|------|------|
| 30 | 方式 | **ポインタイベント**（`pointerdown` / `pointermove` / `pointerup`）。HTML5 の `draggable` にしない |
| 31 | なぜポインタか | ① jsdom は `DragEvent` も `DataTransfer` も持たないため、HTML5 方式は画面テストにまったく載らない。ポインタ方式なら**挿入位置の計算を純粋関数に切り出せて**、依存なしで検証できる ② 既存の `SIGK_SMOKE_DROP` と同じ `webContents.debugger` から `Input.dispatchMouseEvent` を送れば起動確認を機械化できる見込み ③ `shell.js` のつまみに前例がある。なお `file-drop.js` は `types.includes('Files')` で判定しているので、**どちらを選んでもファイルのドロップとは干渉しない** |
| 32 | 掴む閾値 | 5px 動いてから並べ替えを始める。クリックとの取り違えを防ぐ |

## ユーザーに確認したい論点

以下4件は**方向を決める判断**であり、`.claude/CLAUDE.md` 領域1・7 に従い、
実装に入る前にユーザーの確定を仰ぐ。

### 論点1: 抽出（F-02-4）と挿入（F-02-5）を塊⑤へ送るか

`docs/05` は両方を塊④ に割り当てている。しかし**どちらもファイルを書く操作**であり、
書き出し経路（ワーカー・`showSaveDialog`・進捗・中止）は塊⑤ の担当と定めてある。
いま `worker/` も保存ダイアログも無く、`ops` を積むだけでは何も起きない。
挿入はさらに、メイン側の画像読み込み口・PNG/JPEG の判定・2本目の文書の描画を引き連れる。

**推し**: **塊⑤へ送る。**塊④ を「画面の上で並びを組む」、塊⑤ を「それをファイルへ書く」で
割る。塊③ を ③-a／③-b に割ったのと同じ理由（量と依存の向き）である。

### 論点2: 矩形選択（F-02-6 の後半）を第1版から外すか

要件には「Ctrl／Shift クリックおよび矩形選択」と明記されているが、`docs/04` 4-2 には
記述が無く、左ドラッグは並べ替えに割り当て済みで操作が競合する。

**推し**: **外す。**Ctrl / Shift クリックで用は足りる。要望が出てから、
空白部分からのドラッグに限って足す。

### 論点3: 未保存の確認を塊④ で入れるか

`docs/07` の積み残しは、未保存の警告（F-06-5）を塊⑤ 送りにしている。しかし
**dirty になる経路は塊④ で初めて生まれる**ため、このままだと
「編集したタブを閉じると、確認も出ずに編集が消える」状態で塊④ が終わる。

**推し**: **表示（タブの点・ステータスバーの「変更あり」）と、タブを閉じる／終了するときの
確認だけを塊④ に前倒しする。**保存の選択肢はまだ無いので、確認は
「編集内容は保存されていません。閉じると失われます」の**2択（閉じる／キャンセル）**にする。
「保存」を含む3択は塊⑤ で完成させる。

### 論点4: `docs/02` 2-3 の `ops` を改めてよいか

確定事項1〜3 のとおり、ページの並びは「操作の列」ではなく「結果の並び」で持ちたい。
`docs/02` 2-3 は `docs/07` 決定より前に書いた設計で、**undo が書けない**穴がある。
