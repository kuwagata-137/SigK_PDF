## 1. 技術構成の選定

### 1-1. 結論

| 層 | 採用 |
|---|---|
| アプリケーション基盤 | Electron（CommonJS。`main.js` / `preload.js` / レンダラー） |
| レンダラー | 素の HTML / CSS / JavaScript。**ビルドステップなし** |
| PDF 描画 | pdfjs-dist（Apache-2.0） |
| PDF 生成・編集 | pdf-lib（MIT） |
| 日本語フォント埋め込み | @pdf-lib/fontkit（MIT）＋ Noto Sans JP（SIL OFL 1.1） |
| パッケージング | electron-builder → NSIS インストーラー |
| テスト | `node --test` ＋ jsdom |
| CI | GitHub Actions（Ubuntu でテスト、windows-latest でインストーラー生成） |

### 1-2. なぜこの構成か

調査要件レポート第3章は Electron ＋ PDF.js ＋ pdf-lib を推奨しており、選定自体はそれに沿う。加えて本リポジトリでは、**既存プロジェクト CheckListMaker と構成を揃える**ことを優先した。同一作者が保守する2つの Windows デスクトップアプリで、片方が TypeScript ＋ React ＋ バンドラー、もう片方が素の JavaScript という状態は、次の点で不利になる。

- 片方で覚えた手順が他方で使えない。ビルドの詰まり方も別物になる。
- CheckListMaker で確立済みの資産（jsdom テストハーネス、electron-builder の設定、GitHub Actions のワークフロー、preload の API 公開の作法）をそのまま持ち込めない。
- 依存が増えるほど、Electron のメジャーバージョン更新時に追従すべき対象が増える。

ビルドステップを置かない方針は、pdfjs-dist・pdf-lib のどちらでも成立する。両者とも `<script>` から直接読める形の配布物を同梱しているためである（1-3）。

### 1-3. バンドラーなしで外部ライブラリを読む方法

レンダラーは `app://` スキームから配信する（第6章）。`file://` ではないため、ES Modules も通常のオリジンとして扱われ、普通に `import` できる。

npm でインストールしたパッケージのうち、レンダラーが使う配布ファイルだけを `vendor/` へ複製し、`index.html` から読み込む。複製は `scripts/vendor.js`（`npm install` 後に `postinstall` で実行）が行い、`vendor/` は `.gitignore` に入れてリポジトリには置かない。

| ライブラリ | 複製元 | 読み込み方 |
|---|---|---|
| pdf.js（4系以降） | `node_modules/pdfjs-dist/build/pdf.mjs`、`build/pdf.worker.mjs` | `<script type="module">` から `import`。`app://` 上でのみ動く |
| pdf.js の文字マップ | `node_modules/pdfjs-dist/cmaps/` | `cMapUrl` に `vendor/cmaps/` を指定 |
| pdf.js の標準フォント | `node_modules/pdfjs-dist/standard_fonts/` | `standardFontDataUrl` に `vendor/standard_fonts/` を指定。**2026-08-31 追加。**これが無いと標準14書体のテキストだけ描画されないという、原因の分かりにくい不具合になる |
| pdf-lib | `node_modules/pdf-lib/dist/pdf-lib.min.js` | `<script>`（UMD。`window.PDFLib` に載る） |
| fontkit | `node_modules/@pdf-lib/fontkit/dist/fontkit.umd.min.js` | `<script>`（UMD） |

electron-builder の `files` には `vendor/**` を含める。

レンダラー自身のコードは ES Modules にせず、IIFE ＋ `window.SigK` を維持する（`docs/spec-0-foundation.md` 確定事項1・2）。Node から `require()` して純関数を直接テストできる形を保つためである。ES Modules を使うのは pdf.js を読む1点に限る。

### 1-4. 日本語フォントの同梱が必須である理由

pdf-lib が標準で持つ 14 書体（Helvetica など）は **WinAnsi エンコーディングしか扱えず、日本語を描画できない**。F-05-3（フリーテキスト注釈）と F-05-8（テキスト透かし）は日本語入力が前提であるため、TrueType/OpenType フォントを `@pdf-lib/fontkit` 経由でサブセット埋め込みする必要がある。

同梱するフォントは **Noto Sans JP（SIL Open Font License 1.1）** とする。OFL は埋め込み・再配布を許諾しており、商用配布でも条件は「フォント自体を単体で販売しないこと」「派生フォントに元の予約名を使わないこと」であるため、本アプリの用途に支障はない。ライセンス全文は `THIRD-PARTY-NOTICES.md` に収録する。

サブセット化（`subset: true`）は必須である。Noto Sans JP は全体で 5MB を超えるため、埋め込みのたびに全グリフを載せると出力 PDF が肥大する。

## 2. プロセス構成

```
┌─────────────────────────────────────────────────────────────┐
│ メインプロセス  main.js                                      │
│  ・ウィンドウ生成／アプリケーションメニュー                  │
│  ・単一インスタンス制御とコマンドライン引数の集約            │
│    （右クリックメニューからの複数起動を1つに束ねる）         │
│  ・ファイルの読み書き・保存ダイアログ・最近使ったファイル    │
│  ・重い処理のワーカーへの委譲と進捗の中継                    │
└───────────────┬──────────────────────────┬──────────────────┘
                │ IPC                      │ MessageChannel
                │                          │
┌───────────────▼──────────────┐  ┌────────▼──────────────────┐
│ preload.js                   │  │ ワーカー worker/pdf-task.js│
│  contextBridge で API を公開 │  │  utilityProcess で起動     │
│  contextIsolation: true      │  │  結合・分割・変換・透かし  │
│  nodeIntegration: false      │  │  を pdf-lib で実行         │
│  sandbox: true               │  │  進捗を随時報告            │
└───────────────┬──────────────┘  └───────────────────────────┘
                │ window.pdfAPI 等
┌───────────────▼──────────────────────────────────────────────┐
│ レンダラー  index.html ＋ renderer/*.js                      │
│  ・pdf.js による表示（描画は Web Worker）                    │
│  ・UI 状態の管理、undo/redo、注釈の編集                      │
│  ・保存時に編集内容を「操作の列」としてメインへ渡す          │
└──────────────────────────────────────────────────────────────┘
```

### 2-1. 重い処理をワーカーへ出す理由

非機能要件で「重い処理の実行中もウィンドウが固まらないこと」を掲げている。1,000ページの結合や 200MB の PDF のラスタライズをレンダラーのメインスレッドで回すと、その間 UI が完全に止まる。

Electron の `utilityProcess` で Node.js の子プロセスを立て、そこで pdf-lib を動かす。この構成を採る利点は3つある。

1. UI スレッドから完全に切り離せる。処理中の中止（プロセス終了）も確実に効く。
2. 巨大な PDF の展開でメモリを使い切っても、レンダラーごと落ちずにワーカーだけが落ちる。
3. 第2版で Ghostscript や Tesseract を外部プロセスとして呼ぶとき、その受け口をここに置ける。呼び出し側のインターフェースを変えずに済む。

pdf.js の描画は pdf.js 自身が Web Worker（`pdf.worker.mjs`）を持っているため、レンダラー内で完結させる。

### 2-2. 大きなファイルの受け渡し

IPC で `Uint8Array` を渡すと構造化クローンでコピーが発生する。200MB のファイルでは無視できない。

- **第1版**: メインがファイルを読み、`Uint8Array` を IPC で返す単純な形にする。想定ファイルサイズの上限（200MB）ではコピー1回で済むため実用上耐える。
- **メインとワーカーの間**: パスだけを渡し、読み書きはワーカー自身が行う。ファイル本体は IPC に載せない。
- **将来**: レンダラーとワーカーを `MessageChannelMain` で直結し、`ArrayBuffer` を transferable として渡してコピーを避ける。第1版の API 形状（後述 3章）はこの変更を吸収できるようにしておく。

### 2-3. 編集内容の保存の考え方

レンダラーは編集結果の PDF バイト列を自分で組み立てない。**編集の結果**をメインへ渡し、実際の書き換えはワーカーが元ファイルに対して行う。

渡すものは2つに分かれる。**ページの並びそのもの**（`pages`）と、**ページに足すもの**（`ops`）である。

```js
// レンダラー → メイン → ワーカー
{
  source: 'C:\\...\\input.pdf',

  // ページの並び。並べ替え・回転・削除・抽出・挿入は、すべてこの配列で表す。
  // src は元ファイルの 0 始まりページ番号、rotate は元ページの /Rotate に
  // 足す相対角度（0/90/180/270）。配列は「操作の履歴」ではなく「いまの状態」である。
  pages: [
    { src: 0, rotate: 0 },
    { src: 2, rotate: 90 },
    { src: 1, rotate: 0 }
  ],

  // ページに足すもの。こちらは従来どおり操作として積む。
  ops: [
    { type: 'annotate', page: 0, annotations: [ /* ... */ ] },
    { type: 'watermark', pages: 'all', text: '社外秘', angle: 45, opacity: 0.2 }
  ],

  target: 'C:\\...\\output.pdf'
}
```

こうする理由は4つある。

- レンダラーは表示用に低解像度で読んでいることがあり、そこから保存すると元の品質を落としかねない。
- 巨大な PDF バイト列を IPC に往復させずに済む。
- **ページの並びは「結果」で持つほうが曖昧さが無い。**操作の列にすると、`delete` の後の `rotate` のページ番号が削除前か削除後かが決まらず、回転が絶対値か相対値かも決まらない。配列は常に「いま」を表すので、この曖昧さが生まれない。適用も冪等になる。
- **undo/redo が `pages` のスナップショット列として書ける。**逆操作を定義せずに済む。

> **2026-09-01 改訂。**当初この節は編集内容を `ops`（操作の列）だけで持つとし、「undo/redo が
> 操作の列の巻き戻しとして自然に書ける」と書いていた。**これは誤りである。**各 op に逆操作が
> 無く、ページの同一性（どの op のどのページが同じページか）も無いため、列を1つ削っても
> 元の状態には戻らない。抽出・挿入の op も定義していなかった。塊④ の仕様確定
> （`docs/spec-1-5-page-edit.md` 確定事項1〜3・決定4）に伴い、ページの並びを `pages` へ
> 分離した上の形へ改めた。

## 4. レンダラーを分割する方針

CheckListMaker の `index.html` は 388KB の単一ファイルで、CSS も JavaScript も同居している。1画面のアプリでは成立していたが、本アプリは画面数が多く、同じやり方では早期に見通しを失う。

**ビルドステップを置かない方針は維持したまま**、次のように分ける。

- `index.html` には DOM とデザイントークン（`<style>` の CSS カスタムプロパティ）だけを置く。
- スクリプトは `renderer/*.js` に分け、`index.html` から `<script>` で順に読む。
- モジュール間の受け渡しは `window.SigK` 名前空間の下に集約する。ES Modules は使わない。~~`file://` 由来の読み込みで CORS 制約に当たるため~~ **2026-08-31 改訂: 配信は `app://` に決まったのでこの理由は古い。**現在の理由は、各 IIFE を Node から `require()` して純関数を直接テストできる形を保つことにある（`spec-0` 確定事項2）。

```html
<script src="renderer/ui.js"></script>
<script src="renderer/ops.js"></script>
<script src="renderer/viewer.js"></script>
<!-- ... -->
<script src="renderer/app.js"></script>
```

```js
// renderer/ops.js の書き出し方
(function (root) {
  'use strict';
  const SigK = (root.SigK = root.SigK || {});
  SigK.ops = { build, validate /* ... */ };
  // ...
})(typeof window !== 'undefined' ? window : globalThis);
```

末尾の `typeof window !== 'undefined' ? window : globalThis` は、Node の `node --test` から `require()` して純関数を直接テストするための逃げ道である。CheckListMaker のテストハーネスが `index.html` を丸ごと jsdom で起動しているのに対し、本アプリでは**純関数を切り出した層は Node から直接呼べる**ようにして、テストの実行時間を抑える。

`index.html` を jsdom で起動するハーネス（`test/harness.js`）を、画面の結合テストに使う。
~~CheckListMaker から流用し~~ **2026-08-31 訂正: 別リポジトリであり参照しないため、新規に
書き起こした**（`docs/07_開発計画の決定事項.md` 第1章 #5）。同じ「形」（`node --test` ＋ jsdom）は
守っている。

## 5. preload が公開する API

CheckListMaker の作法（機能ごとに名前付きオブジェクト、`available: true` を持たせる）に揃える。

**中身のない口を先に並べない。**各 API は、それを使う機能を作るフェーズで足す
（`preload.js` 冒頭のコメント）。動かない口が `available: true` で並んでいると、
レンダラー側が「使えるはず」と判断して静かに失敗する。

2026-08-31 時点で実際に公開しているもの。

| 公開名 | メソッド | IPC |
|---|---|---|
| `window.appInfoAPI` | `get()` | `app:info` |
| `window.appLogAPI` | `error(entry)` | `log:error` |
| `window.pdfAPI` | `open()` | `pdf:open` |
| | `read(filePath)` | `pdf:read` |
| | `pathForFile(file)` | `webUtils.getPathForFile()`（IPC を通さない。`spec-1-2` 確定事項6） |
| | `onOpenRequest(cb)` | `pdf:openRequest` の受信 |
| | `onDocInfoRequest(cb)` | `pdf:docInfoRequest` の受信 |
| `window.recentAPI` | `list()` / `add(entry)` / `remove(filePath)` | `recent:list` / `recent:add` / `recent:remove` |
| `window.printAPI` | `print(options)` | `print:run`（メイン側で `webContents.print()`。`spec-1-4` 確定事項28〜30） |

これから足すもの。

| 公開名 | 用途 | 足すフェーズ |
|---|---|---|
| `window.taskAPI` | 結合・分割・変換・透かしの実行と進捗購読 | Phase 1 塊⑤（保存で先に要る） |
| `window.shellAPI` | コマンドライン引数の受け取り、既定アプリ設定画面を開く | Phase 5 |

**当初の設計から変わった点。**文書情報は `pdf:info` でメインに取らせる設計だったが、
pdf.js が展開済みの文書から `getMetadata()` で取れるため IPC を増やさずに済んだ
（`spec-1-2` 確定事項11・12）。最近使ったファイルは `pdfAPI.recent` ではなく
独立した `recentAPI` にした。`settings.json` の読み書きであって PDF の操作ではないためである。

以下は設計時に書いた例で、`pdfAPI.info`・`pdfAPI.pickSavePath`・`pdfAPI.recent` は
上記のとおり形が変わっている。`pickSavePath` は塊⑤で入る。

```js
contextBridge.exposeInMainWorld('pdfAPI', {
  available: true,
  // ネイティブの「開く」ダイアログ。戻り値 { path, bytes } / { canceled } / { error }
  open: () => ipcRenderer.invoke('pdf:open'),
  // パス指定で読む（右クリック起動・ドラッグ＆ドロップ用）
  read: (filePath) => ipcRenderer.invoke('pdf:read', filePath),
  // 文書情報。戻り値 { pages, bytes, created, version, encrypted }
  info: (filePath) => ipcRenderer.invoke('pdf:info', filePath),
  // 保存先の選択。戻り値 { path } / { canceled }
  pickSavePath: (suggestedName) => ipcRenderer.invoke('pdf:pickSavePath', suggestedName),
  // 最近使ったファイル（直近10件）
  recent: () => ipcRenderer.invoke('pdf:recent'),
});

contextBridge.exposeInMainWorld('taskAPI', {
  available: true,
  // ops を実行する。戻り値 { taskId }
  run: (spec) => ipcRenderer.invoke('task:run', spec),
  // 実行中タスクの中止
  cancel: (taskId) => ipcRenderer.invoke('task:cancel', taskId),
  // 進捗 { taskId, phase, done, total }
  onProgress: (cb) => {
    ipcRenderer.removeAllListeners('task:progress');
    ipcRenderer.on('task:progress', (_e, data) => cb(data));
  },
  // 完了 { taskId, ok, outputs?, error? }
  onDone: (cb) => {
    ipcRenderer.removeAllListeners('task:done');
    ipcRenderer.on('task:done', (_e, data) => cb(data));
  },
});
```

IPC のチャンネル名は `領域:動作` とする（`pdf:open`・`task:run`・`shell:args`）。CheckListMaker の `rec:start`・`storage:load` と同じ規則である。

戻り値の形も揃える。成功は `{ ok: true, ... }`、キャンセルは `{ canceled: true }`、失敗は `{ error: string }` とし、レンダラー側で例外を投げない。

## 6. セキュリティ

本アプリはユーザーの機密文書を扱い、かつ外部から受け取った PDF を開く。PDF は JavaScript を埋め込める形式であるため、閲覧アプリとしての防御を最初から入れる。

| 項目 | 設定 |
|---|---|
| `contextIsolation` | `true` |
| `nodeIntegration` | `false` |
| `sandbox` | `true`（CheckListMaker は未設定。本アプリでは有効にする） |
| `webSecurity` | `true`（既定のまま） |
| レンダラーの配信 | `app://` スキーム。`protocol.registerSchemesAsPrivileged` ＋ `protocol.handle`。`file://` は使わない |
| CSP | `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; connect-src 'self'`（`'self'` は `app://` のオリジン） |
| pdf.js の設定 | `isEvalSupported: false`（PDF 内 JavaScript の実行経路を塞ぐ） |
| 外部通信 | 行わない。`session.defaultSession.webRequest` で `app:` と `devtools:` 以外の要求を遮断する。`file:` も遮断する（レンダラーはファイルを直接読まない。PDF のバイト列はメインが読んで IPC で渡す） |
| 自動更新 | 入れない。electron-updater を採用しないため、通信の抜け道を作らずに済む |
| 新規ウィンドウ | `setWindowOpenHandler` ですべて拒否する |
| ナビゲーション | `will-navigate` でアプリ外への遷移を拒否する |

`sandbox: true` にすると preload から Node の API を直接呼べなくなる。preload は `ipcRenderer` の橋渡しだけを行い、`fs` や `path` の利用はすべてメインプロセスへ寄せる。上記の API 設計はこの制約を前提にしてある。

## 8. テストの方針

CheckListMaker の `docs/spec-1-2-test-ci.md` の方針を踏襲する。フレームワークを足さず `node --test` と jsdom で回す。

| 層 | 対象 | テストの形 |
|---|---|---|
| 純関数 | `renderer/ops.js`、`worker/op-*.js` | Node から `require()` して直接呼ぶ。fixtures の PDF を入力に、出力 PDF のページ数・回転値・注釈数を pdf-lib で読み返して検証する |
| 画面 | `index.html` ＋ `renderer/*.js` | jsdom で起動し、`test/harness.js` が返す `window.SigK` 経由で内部 API を叩く。pdf.js はスタブに差し替える |
| メイン | `file-io.js`、`platform-win.js` | Electron の `app` / `ipcMain` をスタブして初期化する（CheckListMaker の `createMainStorage()` と同じ手法） |
| インストーラー | NSIS のレジストリ書き込み | 自動テストの対象外。`docs/03_Windowsシェル統合設計.md` の手順書で実機確認する |

画面テストが内部に触る口は **`test/harness.js` が返す `window.SigK` の1本**である。
かつて `renderer/app.js` がテスト専用フック `window.__test__` も載せていたが、誰も
使っていなかったため 2026-09-01 に削除した。テスト専用の口を2本持たないためである
（`docs/spec-1-3-reading.md`）。

`test/fixtures/` には検証用 PDF を置く。ページ数・向き・日本語テキストの有無・暗号化の有無を変えたものを用意し、**ユーザーの実ファイルは使わない**（`.claude/CLAUDE.md` 付則C）。

fixture は**リポジトリにバイナリを置かず、`test/fixtures/build.js` が pdf-lib で生成する**（`.gitignore` に入れる）。CI のテスト前に実行する。生成スクリプトはテキストなので、「3ページ・2ページ目だけ90度回転・日本語テキストあり」といった fixture の意図がコードとして読め、差分にも出る。
