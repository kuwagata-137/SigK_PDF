## 事前調査（2026-09-01・Windows 11 実機で実測）

推測で仕様を書かないため、先に実物で測った。塊③-b・塊④ と同じ手順である。
`docs/spec-1-5-page-edit.md`「塊⑤へ申し送ること」の7件が出発点になっている。

### A. ワーカー（`utilityProcess`）

**最大の未知**は「asar に固めたあとでもワーカーを起動できるか」だった。ミニ asar を
`@electron/asar` で作り、実際に `utilityProcess.fork` して確かめた。

| 調べたこと | 分かったこと |
|---|---|
| asar の中のスクリプトを fork できるか | **できる。**`app.asar/worker.js` を指して `fork` が成功し、`__dirname` は `.../app.asar` になる |
| asar の中から `pdf-lib.min.js` を `require` できるか | **できる。**`require(path.join(__dirname, 'pdf-lib.min.js'))` が通り、`PDFDocument` が取れた |
| 親子のメッセージ | 双方向とも動く。子は `process.parentPort.postMessage(...)`／受けは `e.data`。親は `child.on('message', m => ...)` で**素の値**が届く（`e.data` ではない） |
| 中止（`child.kill()`） | 即座に効く。**元ファイルは無傷**で、書きかけの**一時ファイルだけが残る**（3MB のまま残った）。後始末は呼び出し側の仕事 |

**3段の時間**（1,000ページの fixture・asar のワーカー内）:

| 段 | 時間 |
|---|---|
| read（ディスクから読む） | 3ms |
| load（pdf-lib の解析） | 328ms |
| apply（全ページ逆順の並べ替え＋回転） | 58ms |
| save（バイト列の組み立て） | 680ms |
| 合計 | **1,096ms**・ワーカーの rss 82MB |

`docs/04` 第6章の「1秒を超えそうな処理は進捗と中止」に**ちょうど当たる**。
`docs/spec-1-5` の実測（195.7MB で save 1,634ms）と合わせて、**進捗は必須**である。
`save()` 自体に進捗の口が無いので、**read／load／apply／save／write の5段の切り替わりでしか
出せない**。段の中では進まない。

### B. pdf-lib のオプション（申し送りの訂正を含む）

| 調べたこと | 分かったこと |
|---|---|
| **`updateMetadata` の置き場所** | **`load` のオプションであって `save` のものではない。**`load` 既定（`true`）の時点で Producer が pdf-lib に書き換わる。`save({updateMetadata:false})` を渡しても**効かない**。**`docs/spec-1-5` の申し送りは置き場所を誤っていた**ので、ここで訂正する |
| `updateFieldAppearances` の実害 | **`getForm()` を呼んだときだけ**牙を剥く。`save()` の中は `form = this.formCache.getValue(); if (form) form.updateFieldAppearances();` で、**`getForm()` を一度も呼んでいない文書ではキャッシュが空**なので何も起きない。呼んだ場合は `/AP` を持たない和文の欄で `WinAnsi cannot encode "氏" (0x6c0f)` になる（実測で再現） |
| `addDefaultPage:false` | 全ページ削除して保存すると**0ページの PDF が出来てしまう**（既定 `true` なら白紙 A4 が1枚生える）。塊④ の「最後の1枚は消せない」で塞いである |
| 削除とサイズ | **減らない。**1,000ページを半分削除して `removePage` は 0.2MB のまま、`copyPages` で作り直すと 0.1MB。申し送りのとおり |
| 抽出・挿入の速さ | 抽出3枚 1.3ms、挿入1枚 11.7ms。**軽い** |
| 壊れた PDF | 空 → `No PDF header found`／ヘッダだけ → **例外なし**（0ページの文書として通る）／途中で切った → `Failed to parse invalid PDF obj` |

### C. Windows のファイル事情（上書き保存の実現方法）

| 状況 | 直接 `writeFile` | 一時ファイル → `rename` |
|---|---|---|
| 他のプログラムが**読み取りで開いている** | **成功** | **失敗（EPERM）** |
| 読み取り専用属性 | 失敗（EPERM） | 失敗（EPERM） |
| 何も掴んでいない | 成功 | 成功（上書きされる） |

`os.tmpdir()` からの `rename` は同一ドライブなら通ったが、**ユーザーのファイルは別ドライブに
あり得る**。一時ファイルは**保存先と同じフォルダー**に置く。

外部での書き換えは `size` と `mtimeMs` の比較で検出できる（実測で 47ms の差が出た）。

### D. パスワード付き PDF（pdf.js 側）

暗号化した fixture は**依存を増やさずに作れた**。ISO 32000-1 の Algorithm 2／3／4
（RC4 40bit・`/V 1 /R 2`）を Node の `crypto`（MD5）＋自前の RC4 で書き、約 900 バイトの
PDF を生成した。OpenSSL 3 は RC4 を既定で持たないため RC4 だけ自分で書いている。

| 調べたこと | 分かったこと |
|---|---|
| パスワードなしで開く | `PasswordException`（`name` がそのまま `"PasswordException"`、`code` 1、`message` `"No password given"`） |
| `PasswordResponses` | `{ NEED_PASSWORD: 1, INCORRECT_PASSWORD: 2 }` |
| 聞き方 | `loadingTask.onPassword = (updatePassword, code) => {...}` を**`getDocument()` の直後に代入する**。`updatePassword('user1')` で続行 |
| 間違えたとき | 同じ `onPassword` がもう一度呼ばれ、`code` が 1 → 2 と流れる。**何度でも聞き直せる** |
| 取りやめ | `updatePassword(new Error(...))` で `promise` が reject する |
| オーナーパスワード | ユーザーパスワードと同様に開ける |

### E. 【重大】暗号化 PDF は保存すると壊れる

pdf-lib は暗号化した文書を `load(bytes, { ignoreEncryption: true })` で読めるが、
**復号はしない**。この状態で `save()` すると次のようになった。

- 保存は**成功してしまう**（887 バイトが出力される）
- 出力に `/Encrypt` と `/Filter /Standard` が**そのまま残る**
- 内容ストリームは**暗号化されたまま**（平文の `Encrypted fixture` は現れない）
- 出来た PDF を pdf.js で開くと**正しいパスワードでも開けない**（8秒待っても解決しない）

つまり `ignoreEncryption` を使った保存は**黙ってファイルを壊す**。
**暗号化 PDF は「開けるが保存できない文書」として扱う**（確定事項12）。

### F. 「閲覧はできるが保存だけできない文書」は本当にあるか

`docs/spec-1-5` の申し送りは「pdf.js で開けて pdf-lib で開けない文書がある」としていた。
どういう検体を用意すればよいかを確かめるため、`three-pages.pdf` を5通りに壊して
両方に読ませた。

| 壊し方 | pdf-lib | pdf.js |
|---|---|---|
| 末尾を切る（400B） | `Failed to parse PDF document` | `InvalidPDFException: Invalid PDF structure.` |
| 末尾を切る（半分） | `Failed to parse PDF document` | `InvalidPDFException: Invalid PDF structure.` |
| `startxref` の値を壊す | `TypeError: Cannot read properties of undefined` | `InvalidPDFException: Invalid Root reference.` |
| xref 表ごと消す | `TypeError: Cannot read properties of undefined` | `InvalidPDFException: Invalid Root reference.` |
| オブジェクト参照を壊す | `TypeError: Cannot read properties of undefined` | `InvalidPDFException: Invalid Root reference.` |

**5通りとも両方が失敗した。**単純に壊した PDF では、pdf.js だけが開ける状態は作れない。
つまり**壊れた PDF はそもそもタブにならず、保存の経路に到達しない**。

申し送りが指していた素の `TypeError`（`Cannot read properties of undefined (reading 'Pages')`）は
再現できたので、**ワーカー側で例外の型を選ばずに握る**必要はある。ただしそれは
「開けた文書が保存だけできない」ための備えではなく、**予期しない入力に対する防具**である。

**実際に「閲覧できて保存できない」のは暗号化 PDF である**（実測E）。こちらは pdf.js が
パスワードを聞いて開き、pdf-lib は `load` を断る。確定事項11 と12 の重みが逆で、
**12 が主・11 が従**である。

### G. ページラベル（`/PageLabels`）

ユーザーが「並びに合わせて作り直す」と決めたため、実装できる形かを確かめた。
**独立した2つの経路で測り、結論は一致した。**

| 調べたこと | 分かったこと |
|---|---|
| pdf-lib で書けるか | **書ける。**高レベル API は無いが、`context.obj({ Nums: [...] })` を作って `catalog.set(PDFName.of('PageLabels'), ...)` で入るだけ。`vendor/pdf-lib.min.js` でも同じ |
| pdf.js が読むか | **読む。**`doc.getPageLabels()` が `["i","ii","iii","1","2",...]` を返した。`load` → `save` の往復でも保たれる |
| ラベルを持たない文書 | `catalog.get()` は `undefined`、`getPageLabels()` は **`null`**（例外ではない）。リポジトリの fixture 7本すべてがこれ |
| 展開（読み取り） | 範囲の列を1ページずつへ展開する処理を書き、`/S` 無し・`/P` だけ・`/St`・先頭が 0 でない・空辞書の6様式で **pdf.js と完全一致**した |
| number tree の枝分かれ | `/Nums` 直書きだけでなく **`/Kids` で枝分かれする**。再帰で辿らないと大きな文書のラベルを丸ごと落とす |
| 作り直し（書き込み） | 「元のラベル配列を読む → `plan.map((p) => before[p.src])` → 1ページ1エントリで書く」で、逆順・削除・重複を含む plan すべてで pdf.js の読みと一致した |
| 代償 | 1,000ページで **+4,946 バイト（+2.0%）・組み立て 約1ms**。保存時間に有意差なし。**実質ゼロ** |
| in-place で並べ替えると | ラベルは「ページの中身」ではなく**位置に貼り付いたまま**残る。10ページを逆順にしても pdf.js は元と同じ並びを返した（＝ユーザーの言う「ずれる」を再現） |
| `copyPages` で作り直すと | ラベルは**消える**。作り直しは「ずれ防止」だけでなく「消失防止」でもある |

**【静かな失敗】接頭辞の書き方**。`context.obj({ P: '付-' })` のように**素の JS 文字列を渡すと
`PDFName` に変換され**、`/P /#4ED8-` という名前オブジェクトになる。pdf.js は警告を1行出して
**ラベル全体を `null` にする**。例外は出ないので気づけない。`PDFString.of()` なら ASCII は通るが、
非 ASCII を下位バイトへ切り詰め（`第1部-` → `,1è-`）、`(` `)` `\` も壊す。
**`PDFHexString.fromText()` だけが全て往復一致した。**1,000ページ全部を hex にしても
差は 497 バイト（0.2%）なので、出し分けずに常に hex でよい。

### H. 画像の挿入（F-02-5）

| 調べたこと | 分かったこと |
|---|---|
| 形式の判定 | 先頭バイトで確実に分かる。PNG `89 50 4E 47 0D 0A 1A 0A`／JPEG `FF D8 FF`／GIF `GIF87a`・`GIF89a`／BMP `BM`／PDF `%PDF-`。拡張子は見ない |
| **【重大】`embedJpg` が本物の JPEG で落ちる** | pdf-lib の `JpegEmbedder` が `new DataView(imageData.buffer)` を使い **`byteOffset` を無視する**。Node の `readFileSync` は **4KB 未満のファイルでプール Buffer（`byteOffset≠0`）を返す**ため、**小さい JPEG は必ず失敗する**。`byteOffset` は IPC を越えても保たれるのでレンダラー側でも同じ。`file-io.js` の既存の `toBytes()` を通せば直る |
| `embedPng` が投げる値 | **プリミティブの文字列** `"The input is not a PNG file!"`。`typeof` は `string`、`instanceof Error` は **false**、`e.message` は **undefined**。実体は `@pdf-lib/upng` が先頭8バイトを比べているだけ |
| `embedJpg` が投げる値 | **本物の `Error`**（`message` は `"SOI not found in JPEG"`）。**同じライブラリの中で型が揃っていない。**`spec-1-5` の申し送り「GIF・BMP は message すら持たない値を投げる」は **`embedPng` についてのみ正しい** |
| 例外が IPC を越えると | どちらも `Error` になり、`message` が `Error invoking remote method '<チャンネル>': ...` に汚れる。自前で付けた `code` は消える |
| 0×0 の PNG | **`width=0/height=0` のまま成功してしまう。**pdf.js は 0×0 の MediaBox を無視して **US Letter の白紙**として描く。無言で紙が1枚増える |
| PNG の種類 | グレースケール・パレット・16bit・1bit・アルファ付きすべて通る。CRC を壊したものも通る（検証していない） |
| 透過 PNG | `/SMask` として正しく保たれる。ただし**白い紙が敷かれていない**ので、ビューアの背景色や印刷の下地がそのまま透ける |
| 画素寸法をそのまま紙にすると | 1pt = 1/72 インチなので、スマホ写真 4032×3024 は **1422×1067mm（A4 の6.8倍幅）**。64×64 のアイコンは 23×23mm。**必ず桁の違う紙が混ざる** |
| 基準ページへ内接させると | 挿入ページも A4 のまま、画像だけ縮小されて中央に載る。前後とビューポートが揃う。ただし **64×64 を A4 いっぱいへ拡大すると実効 8dpi のボケた絵**になる |
| メモリ | pdf-lib は PNG を一度 RGBA へ完全展開する。4032×3024 で rss が 61MB → 112MB。JPEG は `DCTDecode` としてバイト列をそのまま入れるので増えない |

**【重要な訂正】`copyPages` でしおりが消えるのは「作り直し方式」のときだけである。**
開いている `PDFDocument` へ `copyPages` ＋ `insertPage` する分には、**その文書のしおり・
AcroForm・内部リンクは保たれた**（実測）。消えるのは、新規文書を作って全ページを
copy し直したときである。塊④ の申し送りはこの区別をしていなかった。

ただし**差し込まれた側**が連れてくるものには問題がある。挿入元のしおり・AcroForm は
来ないが、**AcroForm の `/Widget` 注釈だけがページに付いたまま運ばれる**（フォームとしては
機能しない抜け殻になる）。内部リンクの飛び先はページ木の外を指したままで、
**飛び先ページも一緒に差し込んでも直らない**。

### I. コマンドライン引数と単一インスタンス（F-07-1）

`docs/03_Windowsシェル統合設計.md` 第3章の設計案を実機に当てた。
**設計案に誤りが1つ見つかった。**

| 調べたこと | 分かったこと |
|---|---|

| `app.commandLine` | **使えない。**1つ目のプロセス自身の起動引数しか持たず、`second-instance` の引数は反映されない |
| 引数名の衝突 | `--open`・`--merge`・`--split`・`--to-pdf` は Chromium に横取りされない。対照実験（`--lang=de` は `getLocale()` を変える）で確かめた |
| `additionalData` | **順序を保った受け渡し経路として使える。**`requestSingleInstanceLock(payload)` に渡した値が第4引数へそのまま届く |
| 取りこぼし | **`shell:ready` までメイン側で保持するのは必須。**ただし理由は「読み込み完了前だから」ではなく**「レンダラーがまだ購読していないから」**である。`contextBridge` 経由で購読を始める本アプリの形では、`did-finish-load` で送った分まで消えた（7通中5通） |
| 要求とレンダラーの前後 | 10プロセス同時起動で、最初の `second-instance` は 163〜168ms で届く。レンダラーが `shell:ready` を返すのは約 690ms。**要求のほうが必ず先に来る** |
| 多重起動の取りこぼし | **0件。**N=5 を2回、N=10 を7回、いずれもロック取得1・転送 N−1 で一致した |
| **`PENDING_WINDOW_MS = 400` は短い** | N=10 での隣り合う到着の最大間隔は 194／257／159／432／543／716／**975** ms で、**7回中4回が 400ms を超えた**。10ファイルの結合が複数の要求に割れる |
| パスの順序 | **保証されない。**N=10 の7回のうち1回で7番目と8番目が入れ替わった。`docs/03` の推定は正しい |

### B. 保存できない文書の扱い

| # | 論点 | 決定 |
|---|------|------|
| 11 | pdf-lib で開けない文書 | **防具として置く**（実測F）。単純に壊れた PDF は pdf.js も開けないため、**タブにならず保存の経路へ来ない**。それでも想定外の入力でワーカーが素の `TypeError` を投げることはあるので、例外の型を選ばずに握り、「この PDF は内容が壊れているため保存できません。」に翻訳する。素の文言は表に出さない |
| 12 | **暗号化 PDF** | **保存を断る**（実測E）。`ignoreEncryption` で保存するとファイルが壊れるため、**成功したように見せてはならない**。文言は「パスワードで保護された PDF は保存できません。」。閲覧・印刷は従来どおりできる |
| 13 | いつ判定するか | **保存を押したとき**（開いたときではない）。開く経路に pdf-lib の読み込みを足すと、開くのが 328ms（1,000ページ）遅くなるうえ、保存しない文書にも払わせることになる |
| 14 | 0ページの保存 | 起き得ない。塊④ が最後の1枚を消せないようにしてある（`spec-1-5` 確定事項41）。念のためワーカー側でも `pages.length === 0` を断る |

### C. 上書き保存の実現方法

| # | 論点 | 決定 |

| 15 | 書き方 | **保存先と同じフォルダーに一時ファイル（`<名前>.pdf.sigk-tmp`）を作り、`rename` で置き換える。**書きかけで元ファイルを壊さないため。一時ファイルを `os.tmpdir()` に置かないのは、別ドライブだと `rename` が使えないからである（実測C） |

### I. 挿入（F-02-5）

| # | 論点 | 決定 |
|---|------|------|
| 53 | 受ける形式 | **PDF・PNG・JPEG の3つだけ。**先頭バイトで判定し、**既定拒否**にする。これで WebP・HEIC・TIFF も自動的に断れる |
| 53-2 | **プログレッシブ JPEG** | **検出して断る**（ユーザー確定）。JPEG のマーカーを走査し、**SOF2（`0xFFC2`）があれば**「この JPEG は挿入できません（プログレッシブ形式）。」で断る。pdf-lib の `JpegEmbedder` は SOF2 を受理するが、PDF の `DCTDecode` はベースラインを前提にしており、ビューアによって描けない恐れがある。**検体を作れず実測できていない**ため、壊れたページが黙って入るより断るほうを採る |
| 54 | 断り方 | GIF と BMP は判定表に持ち、名指しで断る（「GIF は挿入できません。PNG・JPEG・PDF を選んでください。」）。それ以外は「対応していない形式です。」 |
| 55 | **バイト列の渡し方** | **必ず `file-io.js` の `toBytes()` を通してから `embedPng`／`embedJpg` へ渡す。**`embedJpg` は `byteOffset≠0` の `Uint8Array` を必ず拒否し、`readFileSync` は **4KB 未満のファイルでプール Buffer を返す**。書き落とすと「小さい JPEG だけ挿入できない」という再現しにくい不具合になる |
| 56 | 例外の扱い | **`embedPng` は文字列を、`embedJpg` は `Error` を投げる。**`e.message` で分岐してはいけない。`e instanceof Error ? e.message : String(e)` で正規化する。ただし**そもそも投げさせない**（先頭バイトで先に判定する）のが本筋である |
| 57 | 0画素の画像 | **断る。**`embedPng` は 0×0 でも成功し、pdf.js は US Letter の白紙として描く。埋め込んだあとに `width > 0 && height > 0` を確かめる |
| 58 | 画素数の上限 | **4,000万画素（約 8000×5000）まで。**pdf-lib は PNG を RGBA へ完全展開するため、4032×3024 で rss が +50MB 増える。超えるものは「画像が大きすぎます。」で断る |
| 59 | 挿入ページの寸法 | **基準ページに内接させる**（画素寸法をそのまま紙にしない）。そのままだとスマホ写真が 1422×1067mm の紙になり、連続スクロールでも印刷でも破綻する |
| 60 | 基準ページの決め方 | **挿入位置の直前のページ。**先頭へ挿すときは直後のページ。文書が空になることは無い（塊④ が最後の1枚を守る）。回転しているページが基準のときは、`rotate` が 90／270 なら**幅と高さを入れ替えた実効寸法**を使う |
| 61 | 拡大の上限 | **100%。**小さなアイコンを A4 いっぱいへ引き伸ばすと実効 8dpi のボケた絵になる。縮小はするが拡大はしない |
| 62 | 透過 PNG | **白い紙を敷く。**`/SMask` は正しく保たれるが、敷かないとビューアの背景色や印刷の下地が透ける。PDF のページは紙であるという見え方に揃える |
| 63 | 差し込んだページの掃除 | **`/Widget` 注釈と、ページ木の外を指す `/Link` を落とす。**挿入元の AcroForm は来ないのに Widget だけが運ばれ、機能しない入力欄の抜け殻が残る。内部リンクは飛び先ページも一緒に差し込んでも直らない |
| 64 | 挿入位置 | 選択中のページの**直前**。選択が無ければ末尾 |
| 65 | 挿入と plan | 挿入したページは plan の外側にある（`src` が元ファイルを指さない）。**`{ insert: <番号>, rotate }` という形を plan に足し**、ワーカーが差し込む。undo は従来どおり plan のスナップショットで戻せる |

| 81 | 飛び先を失ったしおり | **`/Dest`（と `/A` の GoTo）だけを落とし、見出しは残す。**PDF 仕様では「飛び先のない見出し」は正当なので、ページ木の外を指す壊れた状態を書き出さずに済む。しおりツリーの `First`／`Last`／`Prev`／`Next`／`Count` を触らないので、子項目を持つしおりの扱いを決める必要もない |
| 82 | 判定の仕方 | 保存の直前に、しおりツリーを辿って各 `/Dest` の参照先ページが**いまのページ木にあるか**を見る。無ければ落とす。`/Dest` が名前（名前付き宛先）のときは `/Names /Dests` を引いてから同じ判定をする |
| 83 | 名前付き宛先 | 同じ規則で、ページ木の外を指すものは `/Names /Dests` から外す |
| 84 | しおりを持たない文書 | 何もしない。`catalog` に `/Outlines` が無ければ通り抜ける |

### M. 見直しで足した決まり（2026-09-01）

実装したところを読み直して見つけた不具合と、その対処。いずれも回帰テストで固定した。

| # | 論点 | 決定 |
|---|------|------|
| 85 | **しおりで消してよいもの** | **「消えたページを指していると確かめられたもの」だけ。**判定できなかったものには触らない。しおりは必ずしもページを指しておらず、URL を開くもの（`/A /S /URI`）・別ファイルへ飛ぶもの（`/GoToR`）・解決できない名前を指すもの・ページ番号で指すものがある。当初は「解決できなければ消す」にしており、**削除と無関係なウェブリンクまで壊していた** |
| 86 | 宛先がページ参照かどうか | `/Dest` の先頭要素が **PDFRef であるときだけ**ページとして扱う。ページ番号（数値）で指す形は判定できないものとして残す |
| 87 | 名前付き宛先の索引 | **解決できたものだけを載せる。**載っていない名前を指すしおりは「判定できない」側に倒れ、触られない |
| 88 | **読み取り専用のファイル** | **一時ファイルを作る前に断る。**`fs.access(target, W_OK)` で見分ける。読み取り専用と「他のプログラムが開いている」は**どちらも EPERM** で `rename` の失敗だけでは区別できず、当初は読み取り専用のファイルに「他のプログラムで使われています」と出していた |
| 89 | **失敗したときの `.bak`** | **こちらが作った `.bak` は消す。前からあったものは残す。**当初は読み取り専用のファイルで、保存に失敗したのに `.bak` だけが残っていた。前回の保存で作られた `.bak` はユーザーにとって意味のある退避なので、巻き添えにしない |
| 90 | 整合の処理が例外を投げたら | **握らない。**書き込みは最後の段なので、`rebuildLabels` や `pruneDestinations` が転んでも**元ファイルは無傷**である。ワーカーの入口が「保存中に予期しない問題が起きました。元のファイルは変更していません。」に翻訳する。半端に直したものを保存するより、断るほうが安全である（壊れた構造5通りで例外が出ないことは実測した） |
| 91 | 配布物の見張り | **ワーカーを `test/dist-files.test.js` の入口に足す。**ワーカーは `utilityProcess.fork` にパスで渡すため `require` では辿れず、`worker/**` を `build.files` から落としても誰も気づかなかった（塊② の `recent-documents.js` と同じ形）。ワーカーが実行時に読む `vendor/pdf-lib.min.js` も計算したパスなので、別途1件で見張る |
| 92 | 起動確認での保存 | **上書き保存で通す。**「名前を付けて保存」は OS の保存ダイアログが出て自動では押せず、`pickSavePath` を差し替えて逃げることもできない。**`contextBridge` で公開したオブジェクトへの代入は、例外も出さずに黙って無視される**（実測）。`SIGK_SMOKE_SAVE` は入力を出力先へ複製し、その複製を開いて上書きする。`.bak` が出来るかも同時に確かめられる |

### 決定1: 割らない

引き受ける代償は、PR が大きくなることと、⑤-b へ送るつもりだった論点（抽出・挿入の対応形式、
パスワードの聞き方、引数の解釈）をいま確定させる必要があることの2つである。
得られるのは、Phase 1 の完了（＝常用開始。`docs/07` 決定5）が一度に来ることである。

### 決定5: `PageLabels` を作り直す

起草時は「本アプリの画面は 1..N の連番なので、ずれても画面上は分からない」ことを理由に
既知の限界を推した。ユーザーの判断は**保存したファイルの正しさを優先する**というもので、
「他のビューアで開いたときだけ壊れて見える」状態を残さない。

引き受ける代償は実装量である。`/PageLabels` は「このページからこの様式」という**範囲の列**で
持つため、任意の並べ替えのあとは範囲がまとまらず、**1ページ1エントリへ展開する**ことに
なると見込まれる。ファイルサイズと組み立て時間への影響、および `/PageLabels` を持たない
文書の扱いは実測して確定事項へ書く。
