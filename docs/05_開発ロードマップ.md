# SigK PDF 開発ロードマップ

作成日: 2026-08-29（同日改訂。`docs/07_開発計画の決定事項.md` を反映）
関連: `docs/01_製品要件定義.md`（機能ID）／`docs/02_アーキテクチャ設計.md`（モジュール）

各フェーズは「終わったら動くものが手元に残る」単位で切る。フェーズの終わりにはインストーラーを1本作り、実機で触れる状態にする。着手前に仕様を確定させる進め方は `.claude/CLAUDE.md` 領域1に従う。

## Phase 0 — 土台

**目的**: 空のウィンドウが出て、テストと CI が回り、インストーラーが作れる状態にする。

| # | 作業 | 完了の判定 |
|---|---|---|
| 0-1 | `package.json`・`main.js`・`preload.js`・`index.html` の骨組み | `npm start` でウィンドウが出る |
| 0-2 | `scripts/vendor.js`（pdf.js・pdf-lib・fontkit を `vendor/` へ複製） | `npm install` 後に `vendor/` が揃う |
| 0-3 | `app://` スキームの登録と、セキュリティ設定（`sandbox`・CSP・外部通信の遮断・新規ウィンドウの拒否） | 設定値の確認テストが通る |
| 0-4 | デザイントークンの `<style>`（ライトのみ）と画面の骨組み | モックの内容が `index.html` に移り、Chromium で描画が一致する |
| 0-5 | テストハーネス（CheckListMaker `test/harness.js` の移植） | `npm test` が緑 |
| 0-6 | CI 2本（`test.yml`・`build-windows.yml`） | Actions でインストーラーが Artifact に出る |

**論点1 は着手前に決着済み**: `docs/02_アーキテクチャ設計.md` 第9章の論点1（pdf.js 4系の ES Modules 配布が `file://` で読めるか）は、Chromium での実測により「読めない」と判明した。3系へ落とすのではなく、レンダラーの配信を `app://` へ変えることで解決する（`docs/07_開発計画の決定事項.md`）。Phase 0 では `app://` の土台までを作り、pdf.js の読み込みは行わない。

## Phase 1 — 閲覧とページ操作

**目的**: PDF を開いて読める。ページを並べ替えて保存できる。**このフェーズの完了時点から常用を始める**（`docs/07_開発計画の決定事項.md` 決定5）。

常用を始める以上、動作確認用のインストーラーとは要求水準が違う。実ファイルを毎日通すため、後段から2件を前倒しした（決定6）。

| 前倒し | 元の位置 | 理由 |
|---|---|---|
| 上書き保存時の `.bak` 作成 | 6-2 | 保存は `ops` をワーカーが元ファイルへ適用する経路であり、バグは書き損じではなくファイルの破壊として出る。常用初期は `ops` の種類が増えていく最中で、最もバグが出やすい |
| コマンドライン引数の解釈＋単一インスタンス | 5-1・5-2 | これが無いとエクスプローラーからダブルクリックで開けず、毎回アプリを起動してからファイルを開くことになる |

`PENDING_WINDOW_MS`（`docs/03_Windowsシェル統合設計.md` 3-2）の実測は**前倒ししない**。引数の集約が要るのは、右クリックメニューが N 個のファイルに対し N 個のプロセスを起動する `merge`・`split`・`toPdf` の場合であり、いずれも Phase 2 以降である。Phase 1 の `open` は、パスが届くたびにタブを1枚足せば済む。実測は Phase 5 に残す。

### 作業の刻み

15項目を5本の PR に分ける（決定7）。①を先頭に置くのは、`app://` と pdf.js の統合が実際に動くかを最初に確かめ、駄目なら配信方式の判断を早期に見直せるようにするためである。

| 塊 | 内容 | 対応要件 |
|---|---|---|
| ① 表示の最小 | `app://` からの配信、pdf.js の統合、連続スクロール、ズーム | F-01-1、F-01-2 |
| ② 入出力とタブ | ファイルを開く（ダイアログ・ドラッグ＆ドロップ）、タブによる複数文書、最近使ったファイル、文書情報 | F-06-1、F-06-3、F-06-4、F-01-7 |
| ③ 読むための道具 | サムネイルのサイドパネル、テキスト検索・選択・コピー、印刷 | F-01-4、F-01-5、F-01-6、F-01-8 |
| ④ ページ編集 | ページモード（並べ替え・回転・削除・抽出・挿入・複数選択）、`ops` の組み立て、undo/redo | F-02-1〜F-02-7 |
| ⑤ 保存の完成 | ワーカー（`utilityProcess`）と進捗・中止、保存・名前を付けて保存・未保存の警告、`.bak` の作成、パスワード付き PDF の読み込み、コマンドライン引数＋単一インスタンス | F-06-2、F-06-5、F-06-6、F-07-1、非機能 |

塊⑤の着手時に、暗号化 PDF の fixture をどう作るかを決める（`docs/02_アーキテクチャ設計.md` 第9章の論点5）。pdf-lib は暗号化した書き出しに対応しないため、選定済みの依存だけでは作れない。

**このフェーズの終わりに非機能要件を実測する。**起動時間・表示までの時間・メモリを計測し、`docs/01_製品要件定義.md` 第4章の目標値を実測値で見直す。目標に届かない場合、ここで対策を打つ（描画の遅延読み込み、サムネイルの解像度の見直し）。後のフェーズで機能を積んでからでは、原因の切り分けが難しくなる。常用を始める時期と重なるため、体感と数値を突き合わせられる。

## Phase 3 — 変換

**目的**: 画像と PDF を相互に変換できる。

| # | 作業 | 対応要件 |
|---|---|---|
| 3-1 | 画像 → PDF（用紙サイズ・向き・余白・1つにまとめる／個別） | F-04-1〜F-04-3 |
| 3-2 | PDF → 画像（ページ指定・解像度指定） | F-04-4 |

PDF → 画像は pdf.js でキャンバスに描いたものを書き出す。ワーカーは Node 側であり `canvas` を持たないため、この処理だけはレンダラーで行い、書き出しをメインへ渡す。**この非対称は設計の例外である**ため、`worker/op-convert.js` に理由をコメントで残す。

## 進め方についての注記

- 各フェーズの着手前に、そのフェーズの仕様書を `docs/spec-<phase>-<id>-<name>.md` として書き、確定させてから実装に入る（CheckListMaker と同じ命名）。
- フェーズをまたいで機能を先取りしない。Phase 1 の途中で注釈を作り始めない。**ただし Phase 1 の前倒し2件は例外**であり、常用開始という目的から逆算した意図的な繰り上げである。
- 各フェーズの終わりにインストーラーを1本作り、実機で触る。触ってからでないと分からない問題（右クリックの挙動、日本語の描画、大きなファイルの体感速度）が多いためである。
- **Phase 3 以降の順序と中身は、Phase 1 の常用で出た不満を根拠に見直す**（`docs/07_開発計画の決定事項.md` 決定5）。着手前に書いた要件定義の推測より、毎日使って出た不満のほうが優先度の根拠として確かである。

### 検証をどこで回すか

開発環境（Linux コンテナ）では `npm install` も Electron の起動もできない（`registry.npmjs.org` が 403）。三段構えで進める（決定1）。

| 段 | 何を見るか | 場所 |
|---|---|---|
| 手元 | 依存を要しないテスト、`index.html` の DOM とレイアウト | 開発環境（`node --test` ＋ 同梱の Chromium） |
| CI | `npm install` / `npm test` / `npm run dist` が通ること | GitHub Actions |
| 実機 | 体感速度、日本語の描画、右クリックの挙動、`app://` の実動作 | Windows。各フェーズの終わり |

### PR の刻み

- 「終われば何かが新しくできるようになっている」単位で PR を切る（決定7）。作業項目ごとには刻まない。フェーズ丸ごと1本にもしない。
- 作業ブランチで進め、**PR の作成とマージはユーザーの明示指示を待つ**（`.claude/CLAUDE.md` 領域3）。
- リポジトリ設定の「Automatically delete head branches」を有効にしてある。マージ済みのブランチは自動で消えるため、刻んでもブランチが溜まらない（領域6 の制約への対処）。
