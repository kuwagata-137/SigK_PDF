## タスク A: Alt+Tab でアプリに戻ったときの説明の吹き出し（決定81 ③）の記録（2026-10-20）

PR-5 で直した J12 の改訂（`docs/spec-2-5-file-strips.md` 第 J 章）は、「アプリが非活性になったら、キーで移ったという印を外す。活性に戻ると Chromium が、
フォーカスのある要素へ focusin を出し直すと見ている」としていた。この見込みを本物の窓で確かめた。

### やり方

- 開発ツリーの SigK PDF を、**窓を出して**起動した（`SIGK_SMOKE=1`。`SIGK_SMOKE_HIDDEN` は付けない。`--user-data-dir` は scratchpad。窓は 1280×800）。
  テストの表示先ルール（窓を出さない）の例外は、決定81 ③のとおりこの確かめに限る。窓を出す直前にユーザーに知らせた。窓を出したのは 2 回、それぞれ約 30 秒。
- 起動確認の打ち込み（`SIGK_SMOKE_KEYS`）に、アプリの窓のフォーカスを外す `blur-window`（`BrowserWindow.blur()`）と戻す `focus-window`（`focus()`）を足した
  （`smoke-keys-window.js`。`3d18889`・`62fe026`）。戻したあとに出た focusin の相手・活性の要素・`document.hasFocus()` を控える。本物の Alt+Tab のキーは送らない
  （ユーザーのほかの窓を切り替えてしまうため）。
- 筋書き: A.pdf（`three-pages.pdf` の写し）を開き、ページ編集で 1 ページ目を選ぶ → ［左回転］にフォーカスを置く → Tab で［右回転］へ移る（キーで移ったフォーカス）→
  0.9 秒待つ → 窓のフォーカスを外す → 戻す → 0.9 秒待つ。そのあと、マウスで押したボタン・Enter で押したボタン・確認の窓（文書情報）を Esc で閉じたあと、の 3 つを続けた。

### 結果（1 回目）

| 時点 | 説明の吹き出し | 窓 |
|---|---|---|
| Tab で［右回転］へ移って 0.9 秒 | 出た（鍵 `pages.rotateRight`・最前面〔popover〕・下に出す） | 活性 |
| `blur()` のあと | 消えた | 非活性（`isFocused()` が偽） |
| `focus()` で戻して 0.9 秒 | **出ない** | 活性に戻った（`hasFocus` は真）。**Chromium が［右回転］へ focusin を出し直した**（控え `['act-rotate-right']`） |

- J12 の改訂で見込みとしていた「活性に戻ると、Chromium がフォーカスのある要素へ focusin を出し直す」ことを、本物の窓で確かめた。
  出し直された focusin で説明の吹き出しは出なかった（アプリの窓の blur で、キーで移ったという印を外しているため）。jsdom のテスト `test/tip.test.js` の
  「Tab を押したあとでも、アプリが非活性になったら、戻ったときのフォーカスでは出さない」と同じ筋書きを、本物の窓で裏付けたことになる。

### 確かめられなかったこと

- 1 回目の 2 つ目以降の筋書き（マウスで押したボタン・Enter で押したボタン）では、`blur()` が効かず、窓は活性のままだった（そのときの打ち込みは、外れたかを控えに
  書くだけで止めなかった。`62fe026` で、外れないときは止めて problems に書くように直した）。
- 2 回目は、`blur()` のあと窓は非活性と報告されたのに、ページに blur が届かず、説明の吹き出しは出たままで、戻したあとの focusin も出なかった。
  続く `blur()` では窓が活性のままで、打ち込みがそこで止まった。
- 原因は、Windows が、後ろにいるアプリが窓の活性を切り替えることを制限しているためと見ている（確かめてはいない）。アプリの中からの `blur()`・`focus()` では、
  本物の Alt+Tab を安定してまねできない。
- このため、マウスで押したボタン・Enter で押したボタン・確認の窓を閉じたあと、の 3 つの筋書きは、本物の窓では確かめていない。この 3 つは、Chromium に頼る所
  （活性に戻ったときの focusin の出し直し）が上の 1 つ目と同じで、残りは画面の側の判定（マウスで押す・Enter・Esc でキーの印を外す。`renderer/tip.js`）なので、
  jsdom のテスト（`test/tip.test.js` の「キーで移ったフォーカスでは出し、マウスで押して当たったフォーカスでは出さない」と「Alt を押してアプリが非活性になり、
  戻ってフォーカスが当たり直しても出さない」ほか）が守っている。

### 見つけたこと（直さない）

- 確認の窓（文書情報）を Esc で閉じたあと、カーソルが下の段のファイル名の上に残っていると、0.5 秒後にそのファイル名の説明の吹き出しが出た（1 回目の最後）。
  カーソルが説明の吹き出しのある要素の上にあるので、J1（カーソルを載せて止めると出す）のとおりで、不具合ではない。

## タスク C: 保存の外部変更の照合の穴 2 つ（決定81 ①）の記録（2026-10-20）

この節で「書き換え」は、開いたあとでほかのアプリがファイルの中身を変えることを指す（アプリ自身の保存は含まない）。
「元の印」は、元のファイルの大きさと更新時刻の組（`pdf-write.js` の `signatureOf`）を指す。

### 事前調査で分かったこと（2026-10-20）

- 照合の作り: 画面（`renderer/save.js` の `writeTo`）は、開いたときの元の印を `expect` に入れてワーカーへ渡す。ワーカー（`pdf-write.js` の `writeDocument`）は、
  **行き先**のファイルが既にあれば、行き先の今の印と `expect` を比べ、違えば何も書かずに `{ changed: true }` を返す。画面はそのとき確認の窓［上書き］［取りやめ］を出す（spec-1-6 確定事項21）。
- 穴①: 名前を付けて保存で、既にある別のファイルを行き先に選ぶと、行き先の印は元の印と違うので、元が書き換えられていなくても確認の窓が出る（OS の保存の窓が置き換えをもう聞いている）。
- 穴②: ワーカーは保存のたびに、元のファイルをディスクから読み直す。画面のページの並び（開いたときのページの番号で書く）・書き込みの削除（開いたときのファイルの中の参照の番号で書く）・
  モザイクの画像は、どれも開いたときの中身を前提にしている。元が書き換えられていると、新しい中身にそれを当てる。上書き保存では確認の窓で［上書き］を選んだあとにこれが起き、
  名前を付けて保存（別のファイル）と抽出では照らさずにこれが起きる。モザイクがあるときだけは、読む前に元の印を照らして断っていた（spec-4b-6b）。
- pdf.js の `PDFDocumentProxy.getData()`（同梱の `vendor/pdf.mjs`）は、開いたときに渡したバイト列をそのまま返す。画面はタブごとに pdf.js の文書を持っている（`viewer.peek().doc`）。

| C-3 | 画面は、`sourceChanged` か `changed` が返ったときだけ、pdf.js の `getData()` で開いたときのバイト列を取り、鍵 `opened` の写し（`sourceCopy`・`copies`。名前の無い帯と同じ口）にしてもう一度回す。ふだんの保存は今のとおりディスクから読み、バイト列を送らない | 計画 C2・P4 |

### 既知の限界（タスク E）

- フォルダが今あるかを聞き直すのは、保存の窓を出す直前・ツールを選んだとき・アプリの窓が前に出たときだけ。分割・PDF→画像・画像→PDF（画像ごと）の右の欄の「フォルダ」が
  「最後に書き出したフォルダ」か「決めたフォルダ」を指している間に、アプリの窓を前に出したままそのフォルダが無くなる（USB を抜くなど）と、［実行…］は書き出すときに
  失敗の文（「保存先のフォルダが見つかりません。」など）を出して止まる。ツールを選び直すと、元のファイルと同じフォルダに戻る。
- 届かないネットワークのフォルダは、確かめに 1.5 秒待ってから「無い」とみなす。その間、保存の窓が出るのが遅れる。
- 「最後に書き出したフォルダ」は書き出しに成功したときに覚える。PDF→画像は 1 枚書くごとに覚えるので、途中で止めても、それまでに書いた画像のフォルダを覚える（E-6）。
